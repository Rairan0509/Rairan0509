# MANSA · Manual & Safety Assistant

> 승강기 기술사양서와 안전기준을 한 번에 검색해 **작업 절차 · 사양 수치 · 안전 요건 · 기준 차이**를 출처와 함께 답하는 RAG 질의응답 서비스

## 1. 왜 만들었나

- 작업 절차는 **매뉴얼**에, 지켜야 할 기준은 **안전기준**에 흩어져 있어 작업 하나를 확인하려면 여러 문서를 열어야 합니다.
- 매뉴얼 수치와 안전기준 수치가 다를 때 어느 쪽을 따라야 하는지 직접 비교해야 합니다.
- 답을 찾아도 근거 문서와 쪽수를 다시 확인해야 믿고 작업할 수 있습니다.

AI가 사람 대신 답하는 서비스이므로 **"틀린 답보다 답하지 않는 것이 낫다"**를 원칙으로 근거 중심으로 설계했습니다.

## 2. 아키텍처

```
[문서 등록]  PDF 업로드 → 본문·표 분리 추출(PyMuPDF) → 청킹(기술: 페이지·모델·표 행 / 안전: 조항)
            → LLM 부위·작업 태그 → 임베딩 → ChromaDB (tech_docs · safety_docs)

[질문 처리]  질문
            → ① 질문 분석 (LLM: 의도·모델·부위·작업)
            → ② 범위 밖? → 답변 불가 + 확인 부서 안내
            → ③ 모델·부위 모호? → 되묻기 (실제 후보 선택지)
            → ④ 하이브리드 검색: 매뉴얼 + 안전 문서                       ◀ 담당
                 벡터 후보 → 벡터 · BM25 · 태그 순위 → RRF 병합
                 안전 문서는 작업 관계표로 검색어 보강
            → ⑤ 근거 충분? → 아니면 "문서에서 찾을 수 없습니다"
            → ⑥ 답변 생성 (LLM: 절차·사양·안전·기준 차이 + 근거 ID)      ◀ 담당
            → ⑦ 근거 ID·수치가 원문에 있는지 코드로 검사 → 실패 시 재생성(최대 2회)
            → 질문 기록 저장 · 오른쪽 창에 근거 원문 표시                  ◀ 담당
```

질문 1건당 LLM 호출은 **질문 분석 1회 + 답변 생성 1회**를 기준으로 설계해 비용과 지연을 제한했습니다.

## 3. 내가 한 일

### 🔎 하이브리드 검색 (`features/retrieval/`)

정확한 키워드(모델명 `GF210032US`, 조항 번호)와 자연어 질문("로프 교체 기준이 뭐야?")을 모두 처리하기 위해 검색 3종을 결합했습니다.

| 검색 | 잘 찾는 것 | 구현 |
| --- | --- | --- |
| 벡터 검색 | 의미가 비슷한 문장 | OpenAI 임베딩 + ChromaDB |
| BM25 | 모델명·조항 번호 같은 정확한 단어 | 벡터 후보 안에서 키워드 순위 |
| 태그 순위 | 같은 부위·작업을 다루는 청크 | 질문의 부위·작업과 청크 태그 겹침 수 |

- **RRF(Reciprocal Rank Fusion, k=60)**로 세 순위를 합쳤습니다. 점수 척도가 서로 다른 검색 결과를 정규화 없이 순위만으로 합칠 수 있기 때문입니다.
- 태그는 **거르는 조건이 아니라 순위 신호**로 사용했습니다. 태그가 빠진 청크도 후보에서 사라지지 않게 하기 위해서입니다.
- 태그가 하나도 겹치지 않는 청크는 태그 순위에서 제외했습니다. 관계없는 청크가 RRF 점수를 받는 문제를 막기 위해서입니다.
- **안전 문서 검색어 보강**: 안전기준은 모델이 아니라 작업·위치 기준으로 쓰여 있어 질문과 단어가 겹치지 않습니다. 작업 관계표로 작업 위치·위험 유형 단어를 덧붙여, 단어가 겹치지 않는 안전 조항도 찾도록 했습니다. 모델 ID는 오히려 검색을 흐리므로 넣지 않았습니다.

### ✍️ 근거 중심 답변 생성 (`features/qa/`)

- 답변을 **작업 절차 · 사양 수치 · 안전 요건 · 기준 차이** 4개 영역으로 나누고, 영역마다 사용한 근거 청크 ID를 함께 받도록 구조화된 출력(Pydantic 스키마)을 사용했습니다.
- 생성된 답변의 **근거 ID와 수치가 실제 원문에 있는지 코드로 검사**하고, 실패하면 재생성합니다. 끝까지 실패하면 지어낸 답 대신 답변 불가로 처리합니다.
- 안전 요건에는 "AI가 찾은 참고 정보이며 최종 판단은 안전관리자 확인"을 항상 붙였습니다.

### 💬 되묻기 · 질문 기록 · 근거 원문

- 모델이나 부위가 정해지지 않으면 등록된 **실제 후보**로 선택지를 만들어 되묻습니다.
- 대화별 질문 기록을 저장하고, 지난 대화는 다시 생성하지 않고 저장된 답변을 보여 줍니다.
- 답변 오른쪽 창에 근거 원문을 표시하고, 근거 목록을 누르면 원문이 바뀌게 기술 Q&A 화면과 연결했습니다.

## 4. 성능 평가

현장 물류설비 기술·안전 질문 **50문항 테스트셋**(정답 수치·정답 근거 포함)으로 평가했습니다.

| 지표 | 1차 (10/31 11:47) | 2차 (10/31 17:22) | 변화 |
| --- | ---: | ---: | ---: |
| 답변율 (근거 인용 답변) | 56% (28/50) | **62% (31/50)** | +6%p |
| 검색 적중률 | 40.0% | **46.0%** | +6.0%p |
| 출처 정확도 | 40.0% | **46.0%** | +6.0%p |
| 과잉 첨부율 ↓ | 30.4% | **24.2%** | −6.2%p |
| 수치 정확도 | 31.3% | 28.1% | −3.1%p |
| 평균 지연 / 토큰 | 11.6초 / 6,357 | 12.0초 / 6,747 | |

2차 결과의 응답 유형은 답변 31건, 답변 불가 10건, 되묻기 9건이었습니다. 실패 원인은 **검색 17건 · 조회 8건 · 생성 1건**으로, 답변 생성보다 **검색 단계가 가장 큰 병목**이었습니다.

## 5. 트러블슈팅 · 회고: 낮은 답변율

| 구분 | 내용 |
| --- | --- |
| **문제** | 답변율이 62%에 그쳤습니다. 사람 대신 AI가 답하는 서비스는 높은 신뢰가 전제되어야 하는데 이 기준에 미치지 못했습니다. |
| **원인 ① 검증 횟수 부족** | 50문항 평가 1회에 15분 이상, 결과 분석까지 30분 이상 걸렸습니다. 기한을 맞춰야 해서 평가를 2회밖에 돌리지 못했습니다. |
| **원인 ② 통합 테스트만 수행** | 벡터 · BM25 · 태그 검색 3종을 한꺼번에 평가했습니다. 실패가 "검색" 단계라는 것까지는 알았지만, **3종 중 어느 검색이 놓쳤는지** 구분할 수 없었습니다. |
| **피드백 (2팀과 KPT)** | 검색 기능을 **하나씩 분리해 테스트**하고, 기능 단위로 여러 번 반복 개선하라는 피드백을 받았습니다. |
| **개선 방향** | ① 검색 방식별 단독 적중률(벡터만 / BM25만 / 태그만)을 따로 측정 ② LLM 없이 검색만 평가하는 빠른 테스트로 반복 주기 단축 ③ 실패 문항만 다시 돌리는 소규모 회귀 테스트셋 구성 |

### 배운 점

- **평가 체계는 기능보다 먼저 설계해야 합니다.** 기능을 다 만든 뒤에 통합 평가만 하면, 문제가 있다는 것은 알아도 어디를 고쳐야 하는지 알 수 없습니다.
- **빠르게 돌릴 수 있는 테스트가 곧 개선 속도입니다.** 한 번에 30분 걸리는 테스트는 하루에 몇 번밖에 돌릴 수 없습니다. 검색 단계만 따로 떼면 LLM 호출 없이 수 초 만에 확인할 수 있습니다.
- AI 서비스에서는 **답하지 않는 것도 기능**입니다. 근거 검사와 답변 불가 처리 덕분에 답변율은 낮았지만, 근거 없는 답을 내보내지는 않았습니다.
